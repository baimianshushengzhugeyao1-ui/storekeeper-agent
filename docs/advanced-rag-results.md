# 增强 RAG：实测结果与边界

## 做了什么

针对中文问题检索英文规则失败、无答案问题仍返回上下文的问题，新增
LangGraph 检索子图：中文查询改写、BM25 与 Chroma 向量双路召回、RRF
融合、LLM 证据重排与充分性检查。Python 核验片段编号和原文引用，忽略
排版空白差异，但不忽略数字或措辞差异。无证据或检索出错时转人工。

没有换 Embedding 模型，没有部署 cross-encoder，没有引入 Azure Search，
也没有知识图谱或自主无限搜索。原向量方案仍可通过配置切回。

## 数据和实验过程

- 原 v1：英文40题（44个标注证据）、中文10题、无答案6题。已知回归集。
- 新 v2：英文8题（10个证据）、对应中文8题（10个证据）、无答案4题。
  Codex 编写的合成问题，第一次运行前冻结；不是用户数据或独立人工标注。
- 同一语料、切块和 Top3 上限，对照 dense、hybrid、translated_hybrid、enhanced。
- 首轮共76题×4组，出现11个模型连接失败。保留首次失败，对这11项单独串行补测，
  未对语义失败项反复调用挑结果。补测均成功。
- 新题暴露原文换行导致引用检查误拒的问题；只修复空白归一化，并离线重放
  已保存的模型输出。3题改变。这不是独立新一轮真实调用，也不能再将 v2
  视为未接触的最终测试集。下一次优化应另加独立留出题。

## 结果

- v1 中文证据 Recall@3：原向量60%；纯混合60%；查询改写后100%；增强100%。
  改善主要来自跨语言改写，不能把收益都归给 BM25 或重排。
- v1 英文证据 Recall@3：原向量100%；纯混合97.73%；增强100%。
  盲目加混合检索会退步，不能认为复杂方案必然更好。
- v2 中文证据 Recall@3：原向量40%；改写后混合100%；引用修复重放后增强100%。
- v2 英文证据 Recall@3：原向量80%，增强仍80%；其中一个双问题缺少
  保修起算证据，增强选择转人工。该失败仍保留。
- v1/v2 共10条无答案题：原方案全部返回上下文；增强均返回空证据并转人工。
  这只是这10个探针的表现，不代表所有无答案问题都能识别。
- v1 英文增强选择证据的 precision 为44/47=93.62%，原固定三段为44/120=36.67%。
  增强返回不超过3段的最小证据集，分母发生变化，不能将此写成回答准确率提升。
- 有效结果记录中，原检索中位耗时约1.58秒，增强约5.75秒。三并发本地评测下的
  记录值，包含部分串行网络补测，不是严格串行性能基准，也不是生产SLA。
- 首轮可记录成功调用与网络补测共114次、156089 Token。没有包含应用冒烟调用，
  网络失败若产生了服务端用量可能未被客户端记录；这不是账单成本。

## 应用与代码验证

- 最终140项本地测试通过，包括9项新增检索测试。
- 真实模型应用处理函数冒烟：中文保修起算问题正常回答并引用 warranty.md；
  分期付款问题转人工，无引用。两例不能代表端到端准确率。
- 跨语言改写仍可能漂移，LLM评分仍可能误判。原文引用检查只验证来源归属，
  不证明因果解释正确。最终回复仍使用既有生成模型。
- API 仍有同进程全局锁；增加模型步骤会占用更多处理时间。不是高并发服务。
- 真实 Shopify 未联调，订单继续使用模拟数据。

原始过程在 `var/evaluations/advanced_rag_v1/`：`frozen_manifest.json`、
`report.json`、`transport_recovery.json`、`evidence_replay.json`、
`application_smoke.json`。发布副本的对应文件存于 `evidence/advanced_rag/`。

## 可以用于简历的表述

针对中文查询英文店铺规则的漏召回问题，基于 LangGraph 实现查询改写、
BM25/向量混合召回与 RRF 融合，增加结构化证据筛选和原文引用校验，
资料不足时转人工；在原10条中文合成回归题中，Recall@3 从60%提升至100%，
并在10条无答案探针中验证转人工分支，保留新增题失败与额外模型开销。
